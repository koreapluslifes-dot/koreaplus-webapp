The build-seo.cjs output dirs (`faq/ ja/ zh/ es/ guide/ places/ itinerary/ blog/` + `explore.html sitemap.xml`) are **NOT git-tracked** — only `sitemap.xml` is. They deploy by copying to the Lightsail box (IP `18.207.55.50`, confirmed by user 2026-06-15), dir `/opt/bitnami/wordpress/guide`, PEM `C:\Users\juksu\Documents\blog\koreaplus-lifes\LightsailDefaultKey-us-east-1.pem`, user `bitnami`.

**SSH to prod requires the user's explicit approval naming the target** (auto-mode classifier blocks it otherwise).

`bitnami` has passwordless `sudo` but **cannot write `/guide` subdirs directly** (some are owned by UID 197609 from earlier Windows-origin copies). So plain `scp` fails with Permission denied. Working method:
1. `tar czf /c/tmp/kp.tgz <dirs/files>` (paths relative to repo root)
2. `scp` the tarball to `/tmp` on the server (writable)
3. `ssh … 'sudo tar xzf /tmp/kp.tgz -C /opt/bitnami/wordpress/guide && sudo chown -R bitnami:daemon <paths> && sudo find <paths> -type f -exec chmod 644 {} + && rm /tmp/kp.tgz'`

GOTCHA: `tar xzf` recreates parent dir entries with the LOCAL (Windows) perms, which clobbers the prod dir to `drwxrw----` (no o+rx) and 403s everything under it (Apache runs as `daemon`). After EVERY extract, run `sudo find <touched top-level dirs e.g. ja zh es guide> -type d -exec chmod 755 {} +` AND `-type f -exec chmod 644 {} +` — chmod the PARENT lang dir too, not just the new subdir.

`deploy-to-guide.ps1` (root files + an SEO-dirs block I added) is the user-run alternative but uses plain `scp` (works only where bitnami owns the dir). Worker deploys via `npx wrangler deploy src/worker.ts`. Instant indexing: POST url list to `api.indexnow.org/indexnow` + `bing.com/indexnow` with key file `kp7e3f1c9a2b5d48069e3f1c9a2b5d48.txt` (Google sitemap ping is dead since 2023 — use GSC). Prod HTML is `cf-cache-status: DYNAMIC` so changes show immediately. See [[cloudflare-fronting]], [[agoda-api-usd-only]].

**Apache docroot + URL structure (verified 2026-06-26, critical for verifying live):** the active vhosts are `/opt/bitnami/apache2/conf/vhosts/wordpress-vhost.conf` + `wordpress-https-vhost.conf`, both `ServerName koreaplus-lifes.com` with **`DocumentRoot /opt/bitnami/wordpress`** (NOT `/guide`). The whole KoreaPlus travel app lives at web **`/guide/`** (= `/opt/bitnami/wordpress/guide/`) because `build-seo.cjs` has **`BASEP='/guide/'`**. So canonical SEO URLs are doubled: a city guide is `koreaplus-lifes.com/guide/guide/things-to-do-X.html` and a localized one is `koreaplus-lifes.com/guide/ja/guide/things-to-do-X.html` (file at `/opt/bitnami/wordpress/guide/guide/…` and `…/guide/ja/guide/…`). Root app files = `/guide/about.html`, `/guide/compare.html`, etc. **When verifying live, use these doubled `/guide/guide/` paths — a request to the single `/guide/things-to-do-X.html` 404s into WordPress, which 301-redirects to `https://koreaplus-lifes.com` (home). Always check WITHOUT `curl -L` (a `-L` follow masks the 301 as a 200 home page = false pass).**

**Perm GOTCHA fix:** after `tar xzf`, fix perms so Apache (`daemon`) can serve — dirs need `o+rx`, files `o+r`. tar recreates nested dir entries with local Windows 700 (`drwx------`) → **403** for every page beneath them. Use a **loop** until clean: `chmod -R a+rX $R` (or `find -type d -exec chmod 755`), then assert `sudo find $R -type d ! -perm -001 | wc -l` is 0; repeat if not. (Use octal `-perm -001` for the check — symbolic `-perm -o+x` is misparsed by find and silently returns nothing = false pass.) `deploy-seo.sh` (repo root) now does tar→scp→extract→**perm-loop+assert**→IndexNow.

**ROOT CAUSE of the intermittent/whack-a-mole 403s (2026-06-26):** a **CONCURRENT SFTP deploy from another session** (the K-pop/K-beauty dispatch deploy, which writes the SAME shared `/opt/bitnami/wordpress/guide` tree incl. all `<lang>/` dirs) was re-creating 700 dirs WHILE I fixed them — each verify sweep showed a *different* lang dir 403 (zh/es → ko/fr → de → pt) plus transient **500s** on files being overwritten mid-request. Diagnosis: `ps -eo … | grep sftp-server` showed an active `sftp-server` PID and `find $R -mmin -2` showed fresh writes under `id/kpop/`, `id/blog/`. **Don't fight a perm race** — detect concurrent activity (active sftp-server proc OR files modified in the last ~60–120s), WAIT for it to quiesce, THEN do the final perm loop. After it settled, full sweep = 113/113 200 and perms stayed stable. When verifying after a possible concurrent deploy, also re-check content markers (the other deploy could overwrite your pages with an older build).
